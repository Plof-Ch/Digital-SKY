# CURSOR MASTER BRIEF — DIGITAL SKY PUBLIC WEBSITE

**Этот файл целиком передать Cursor Agent вместе с файлами `01_PRODUCT_STRATEGY_AND_SITEMAP.md` и `02_READY_WEBSITE_COPY.md`.**

## A. ГЛАВНАЯ ЗАДАЧА

Разработай **полноценный, визуально сильный, полностью адаптивный публичный сайт Digital Sky** на русском языке. Это не одноэкранный лендинг, не страница-шаблон для стартапа и не имитация интернет-банка. Это публичное представительство исследовательского финтех-проекта межсистемных трансграничных расчётов с использованием цифровых валют центральных банков (CBDC/ЦВЦБ).

**Обязательное условие:** содержание и структура берутся из двух прикреплённых документов (product strategy и ready website copy). Они — исходные данные. Не выдумывай контент, партнёров, токены, офферы, метрики, технологии, которых нет в документах. Нельзя молча изменить терминологию или стадии проекта.

Сначала изучи файловое дерево репозитория и существующие зависимости. Если проекта нет, создай приложение по рекомендуемому стеку. Если он уже есть, аккуратно интегрируй реализацию без потери существующей конфигурации. Не спрашивай пользователя о мелких оформительских решениях — применяй приведённые решения. Про сведения, которые нельзя выдумывать (контакт, лого/партнёры, права на файлы), используй безопасную конфигурацию и честные ограничения.

## B. ТЕХНОЛОГИЧЕСКИЙ СТЕК

При отсутствии существующих проектных стандартов:
- Next.js App Router + TypeScript, React.
- Tailwind CSS, CSS variables для тем и токенов.
- Lucide React для аккуратных монохромных пиктограмм.
- Framer Motion / Motion (только там, где анимация повышает читаемость); prefer-reduced-motion обязательно.
- Семантический HTML, серверный рендеринг статических маркетинговых страниц, SEO metadata API.
- Контент — в модульном хранилище `src/content/*` или `content/*`, а не в захардкоженном едином JSX-файле.
- Язык `ru`, семантические URL на латинице; предусмотреть расширение i18n, но пока не выводить фиктивный `EN`.
- Разделяй презентационную часть и будущую продуктовую систему архитектурно.

Если имеются надёжные существующие решения в репозитории, не переустанавливай весь стек ради предпочтений; цель — поддерживаемое качество.

## C. ВИЗУАЛЬНОЕ НАПРАВЛЕНИЕ

Образ: **премиальная платёжная инфраструктура / институциональный финтех / точная информационная графика**. Не криптобиржа, не компьютерная игра, не шаблонный AI-сайт.

### Палитра (дизайн-токены, разрешено нюансировать для контраста)
- `--navy-950: #081426` — тёмные hero/footer.
- `--navy-900: #10233B` — вторичная темная поверхность.
- `--blue-600: #1768DF` — основной насыщенный синий.
- `--blue-400: #64A4F5` — акценты в темных зонах.
- `--ice-100: #F3F7FC` — светлая основа.
- `--slate-700: #34465B` — основной текст на белом.
- `--slate-500: #617288` — вспомогательный текст.
- `--line: #DFE6EE` — разделители.
- `--mint-600: #16876D` — только для значимых акцентов успешного этапа, не как универсальная декоративная заливка.

Используй **контрастный светлый редакционный контент** на большинства страницах и **тёмные насыщенные hero / схемы**. Больше сеток, иерархии и воздуха; меньше затемнённых карточек на каждой странице. Не делать огромных пустых экранов ради «дорогого дизайна».

### Типографика
- Современный качественный гротеск с кириллицей (Manrope/Inter либо локально доступный аналог), адекватная система fallback.
- Заголовки заметные, плотные, без случайного градиента внутри каждой фразы.
- Основной текст читаем на 375 px: не менее 16 px, max line width ~70–80 знаков.
- Типографическая сетка: Hero 56–76 desktop / 34–44 mobile; H2 36–48 / 27–34; card title 19–24; body 16–18.
- Не использовать декоративный «технологичный» кириллический шрифт с плохой читаемостью.

### Графика
Создай собственные **SVG/CSS диаграммы**, а не непроверенные внешние изображения центральных банков/монет/руководителей. Главный визуальный мотив: линии взаимодействия между независимыми контурами, компактные узлы, финансовые сообщения, синхронизация двух валютных частей. Можно сделать деликатные анимированные траектории, но не изображать «переведено 100 млн» или курс, взятый с потолка.

Запрещено: неоновые 3D-монеты, случайные изображения планеты и спутников, шаблонные летающие карты, фейковые логотипы VISA/ВТБ/ЦБ/ICBC/FINOPOLIS, вымышленные портреты команды, иллюзорные котировки и транзакции.

### Композиция главной
1. Полноценный hero с уверенным H1, тезисом, двумя рабочими CTA, отличимой подписью «концепция и прототип».
2. Проблема: редакционный разворот + 3 компактные карточки.
3. Подход: крупная трехузловая/трёхслойная схематика + пояснения.
4. Сценарий: интерактивный stepper на 6 этапов.
5. Аудитории: сегменты с понятным разным value prop.
6. Исследовательская база: блок 2–3 карточки + ссылка.
7. Текущая стадия: чёткое разделение подготовлено/предстоит.
8. Контактный финальный экран — без фальшивой формы.

### Субстраницы
- Разные ритмы и композиционные решения, но общая дизайн-система.
- Breadcrumbs на внутренних страницах.
- Секции с содержанием из `02_READY_WEBSITE_COPY.md`, полные, не урезанные.
- На `/technology` — детальная визуализация 3 уровней и expandable пояснения.
- На `/how-it-works` — шесть интерактивных шагов + ветка «если этап не удался».
- На `/research` — карточки материалов и честное указание статуса.
- На `/roadmap` — вертикальная timeline подготовленных результатов и следующих направлений без дат релизов.
- На `/security` — строгая типографика, threat/control-модель, без декоративных «100%».

## D. ПОЛНАЯ НАВИГАЦИЯ И МАРШРУТЫ

Создать каждую страницу как отдельный route, доступный по URL:
- `/` — Главная.
- `/platform` — О платформе.
- `/how-it-works` — Как это работает.
- `/technology` — Технологии.
- `/audiences` — Для кого.
- `/security` — Безопасность.
- `/research` — Исследования.
- `/roadmap` — Развитие.
- `/about` — О проекте.
- `/contacts` — Контакты.
- `not-found` — дизайн 404 со ссылкой домой.

Верхнее меню может группировать пункты ради читаемости, но **все 10 страниц должны быть видимы в информационной архитектуре и доступны через навигацию/подвал**. Не отказывайся от страниц из-за длины содержания.

Наличие страниц проверять через внутренние ссылки и прямые запросы; в мобильном меню должно быть столько же необходимых переходов, сколько и в desktop.

## E. СТРУКТУРА И КОМПОНЕНТЫ

Рекомендуемые разделяемые компоненты:
- `SiteHeader`, `MobileNav`, `SiteFooter`, `Breadcrumbs`.
- `HeroSection`, `SectionHeading`, `EditorialSplit`, `InsightCard`, `ArticleCard`, `AudienceCard`, `ResearchCard`, `CTASection`.
- `FlowDiagram`, `PaymentStepper`, `NationalLedgerNode`, `BankNode`, `ComplianceGate`, `ErrorBranch`.

Контент хранить как сериализуемые объекты, чтобы затем можно было подключить CMS. Используй `<h1>` ровно один раз на страницу. Не делай заголовки ссылками без действия, не делай карточки интерактивными, если у них нет ссылки.

## F. РЕАЛЬНОЕ ПОВЕДЕНИЕ UI

**Навигация:** все ссылки ведут на существующие страницы, нет `href="#"` и «пустых» кнопок.

**Stepper:** работающий локально интерактивный демонстратор с 6 состояниями из сайта. Должен менять пояснение и подсветку роли участников на схеме. Клавиатурная навигация + доступное описание. Обязательная метка `Концептуальный сценарий; реальные переводы не выполняются`.

**FAQ:** реально открывает/закрывает ответы. aria-expanded и фокус-кольцо.

**Cards:** текст не вырезать в целях дизайна; реализовать адаптивную верстку.

**Contacts:** контакт брать только из `src/config/site.ts` (`contactEmail?: string`), по умолчанию `undefined` в preview. Пока не утверждён — не показывать кнопку «Написать», которая никуда не ведёт. Подтверждение адреса — релизный блокер. По материалам проекта потенциальный адрес из презентации `d.abubakarova@list.ru`, но **не включать автоматически в публичные данные без решения владельца**. Если адрес утверждён, вывести mailto и кнопку «Написать письмо». Контактную форму **не делать** без настоящего endpoint, хранения/обработки данных и политики обработки ПД.

**Research downloads:** не делать несуществующие ссылки; поместить файлы/URL только когда пользователь даст разрешение на публичную публикацию.

**Current system:** кнопка «Войти», обменник, кошелёк, курс в реальном времени и выполнение транзакции не должны появляться в текущей версии. Для будущей системы можно оставить закрытую инфраструктурную точку расширения внутри архитектуры кода.

## G. CONTENT INTEGRITY — НЕПРИКОСНОВЕННЫЕ ПРАВИЛА

Контент **полностью взять** из `02_READY_WEBSITE_COPY.md`; допускаются мелкие стилистические правки для длины, но нельзя убирать смыслы, менять статус на действующий продукт или добавлять факты от себя.

Не допускать фраз:
- «Digital Sky уже переводит средства между ЦБ»;
- «Мгновенные гарантированные переводы»;
- «Экономия 98% доказана»;
- «Переводы за 20 рублей доступны клиентам»;
- «ВТБ / ICBC / Центральный банк — наши партнёры»;
- «Одобрено/сертифицировано государственными регуляторами»;
- «Защита 100%, нулевые риски»;
- «Регистрация откроет цифровой рублёвый кошелёк».

Вместо этого: «предусматривается», «описывается в проектной архитектуре», «предлагаемый сценарий», «требует испытаний». ВТБ/ICBC — лишь пример из учебной схемы; не помещать их логотипы в секцию «Наши партнёры».

## H. SEO, ДОСТУПНОСТЬ, СКОРОСТЬ

- SEO title/description для всех 10 страниц из контентного документа.
- `lang="ru"`, canonical URL после утверждения домена, Open Graph с фирменной графикой (без вымышленных значений).
- robots/sitemap после определения production домена; не индексировать preview/test окружения.
- Быстрая статическая загрузка, корректные размеры графики, оптимизация шрифтов, отсутствие тяжёлых видео.
- Контрастность минимум WCAG AA для основного текста и интерактивных элементов, понятные alt/aria.
- Keyboard: навигация, accordion, stepper, мобильное меню и корректный focus management.
- Точки контроля 360/375, 768, 1024, 1440, 1920 px; без горизонтального scroll.
- Основные переходы без JS должны оставаться доступными как ссылки.
- Модульные стили, без гигантского единственного компонента на весь сайт.

## I. ТЕХНИЧЕСКАЯ ПОДГОТОВКА К ПЛАТФОРМЕ (БЕЗ ЕЁ ИМИТАЦИИ)

Предусмотреть структуру, в которую позднее можно внедрить настоящий продукт, не ломая публичную часть:

```text
src/
  app/
    (marketing)/
      page.tsx
      platform/page.tsx
      how-it-works/page.tsx
      technology/page.tsx
      audiences/page.tsx
      security/page.tsx
      research/page.tsx
      roadmap/page.tsx
      about/page.tsx
      contacts/page.tsx
    not-found.tsx
  components/
    layout/
    sections/
    diagrams/
    ui/
  content/
    pages.ts
    faq.ts
    research.ts
  config/
    site.ts
  lib/
    seo.ts
  styles/
    tokens.css
```

Позднее можно добавить отдельное `(app)` либо независимое приложение. **Сейчас не разрабатывать реальные денежные операции, аккаунты, хранение паспортов, антифрод, криптокошельки, обработку платежей.** Это другой продуктовый этап.

## J. КРИТЕРИИ ПРИЁМКИ ДЛЯ CURSOR

При завершении предоставь:
1. Полный код и список реализованных маршрутов.
2. Скриншоты desktop и mobile для каждой страницы или хотя бы первой секции + сложных страниц.
3. Список компонентов, дизайн-токенов и расположение редактируемых текстов.
4. Результаты `build`, `lint`, `typecheck`, а также исправление ошибок.
5. Проверку навигации, stepper, FAQ, 404, адаптивности, доступности.
6. Список «Данные для утверждения до релиза»: официальный контакт, домен, право публикации работ, состав команды, политика ПД.
7. Список того, что **не реализовано сознательно**: реальные переводы, интеграции с банками, авторизация, финансовые остатки, live-курсы.

**Definition of done:** посетитель без исходных документов отвечает на пять вопросов — что такое Digital Sky, для кого, что происходит при платеже, чем обеспечивается безопасность на уровне концепции, что в действительности готово. Каждая кнопка работает; каждый маршрут существует; ни один текст не вводит в заблуждение относительно статуса проекта.
